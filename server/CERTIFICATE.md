# Схема доверия, PKI и E2E-шифрования

Документ описывает модель безопасности, инфраструктуру открытых ключей (PKI), жизненный цикл сертификатов и протокол сквозного шифрования (E2EE) в проекте **SUN_IN_alpha**.

---

## 1. Роли участников системы

1. **Сервер (Private Root CA / Регистратор доверия)**:
   - Владеет 4096-битным закрытым ключом корневого удостоверяющего центра `private_ca.key`.
   - Публикует доверенный сертификат `private_ca.crt` (раздается клиентам).
   - Проверяет корректность CSR (Common Name, подпись запроса) и выпускает клиентские X.509 сертификаты сроком на 365 дней.
   - Фиксирует выданные сертификаты в базе данных PostgreSQL, гарантируя уникальность связки `nickname <-> cert`.

2. **Клиент (Браузер / Отправитель)**:
   - Генерирует ключевую пару RSA-2048 локально в браузере через Web Crypto API. Закрытый ключ **никогда не покидает устройство**.
   - Формирует запрос на сертификат PKCS#10 (CSR) через библиотеку `@peculiar/x509`.
   - Сохраняет выданный сертификат и закрытый ключ в `localStorage` браузера.
   - Может экспортировать резервную копию в зашифрованный файл `<nickname>.enc` (пароль + AES-256-GCM).

3. **Получатель сообщения (Собеседник)**:
   - Предоставляет свой открытый ключ через X.509 сертификат, заверенный доверенным CA.
   - Использует собственный закрытый ключ для расшифровки сессионного ключа AES.

---

## 2. Гарантия «1 сертификат на 1 ник»

Сервер обеспечивает строгую защиту от подделки и перехвата никнеймов:

1. **Первичный ключ в PostgreSQL**:
   ```sql
   CREATE TABLE IF NOT EXISTS certificates (
       nickname VARCHAR(255) PRIMARY KEY,
       cert_pem TEXT NOT NULL,
       created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
   );
   ```
2. **Блокировка повторного выпуска**:
   При получении пакета `cert_enroll` сервер проверяет наличие записи в таблице `certificates`:
   - Если сертификат уже был выдан для этого ника — запрос отклоняется с ошибкой `Сертификат для никнейма <ник> уже был выдан ранее`.
3. **Верификация при авторизации (`auth_init`)**:
   Сервер проверяет, что сертификат, предъявленный клиентом, байт-в-байт совпадает с сохраненным в базе данных. Злоумышленник не сможет войти под чужим ником, даже если у него есть другой сертификат.

## 3. Хранение identity на клиенте

Вместо сохранения незащищенных файлов на жестком диске клиент сохраняет identity в изолированном хранилище браузера:
- **`localStorage.getItem('sun_in_key_<nickname>')`**: закрытый RSA-ключ в формате PKCS#8 PEM.
- **`localStorage.getItem('sun_in_cert_<nickname>')`**: выданный сервером X.509 сертификат PEM.

### Резервное копирование и перенос (`.enc`):
- **Экспорт**: Закрытый ключ и сертификат упаковываются вместе и шифруются алгоритмом **AES-256-GCM**. Ключ формируется из пароля через **SHA-256**. Файл скачивается как `<nickname>.enc`.
- **Импорт**: Пользователь загружает файл `.enc`, вводит пароль — данные расшифровываются и восстанавливаются в `localStorage` браузера.

## 4. Жизненный цикл аутентификации (Challenge-Response)

```text
КЛИЕНТ                                                   СЕРВЕР
  │                                                        │
  │─── 1. auth_init (nickname, client_cert) ──────────────>│
  │                                                        │ Проверка:
  │                                                        │ - Подписан private_ca.crt
  │                                                        │ - Не просрочен
  │                                                        │ - CN == nickname
  │                                                        │ - Совпадает с записью в БД
  │                                                        │
  │<── 2. auth_challenge (nonce: 32 случайных байта) ──────│
  │                                                        │
  │ Подпись nonce закрытым ключом:                         │
  │ signature = RSA_sign(nonce, mySignKey)                 │
  │                                                        │
  │─── 3. auth_proof (signature: Base64) ─────────────────>│
  │                                                        │ Верификация:
  │                                                        │ RSA_verify(signature, nonce,
  │                                                        │            cert.public_key)
  │                                                        │
  │<── 4. event (auth_success) ────────────────────────────│ Клиент авторизован!
```

## 5. Сквозное (E2E) шифрование сообщений

При отправке сообщения от Алисы к Бобу:

1. **Запрос ключа**: Если Алиса ещё не имеет сертификата Боба, она отправляет `key_request(to='bob')`.
2. **Ответ**: Сервер присылает `key_response(client_cert=...)`.
3. **Валидация**: Алиса проверяет, что сертификат Боба подписан доверенным CA, срок действия корректен и `CN == bob`.
4. **Извлечение ключа**: Библиотека `x509.js` извлекает открытый ключ RSA-OAEP:
   ```javascript
   const cert = new x509.X509Certificate(certPem);
   const bobPubKey = await cert.publicKey.export({ name: "RSA-OAEP", hash: "SHA-256" }, ["encrypt"]);
   ```
5. **Гибридное шифрование**:
   - Генерируется одноразовый сессионный 256-битный ключ `aes_key` и 12-байтный `nonce`.
   - Текст сообщения шифруется алгоритмом `AES-256-GCM`.
   - Сессионный `aes_key` шифруется открытым ключом Боба по схеме `RSA-OAEP SHA-256`.
6. **Доставка**: Сервер передает пакет `message` Бобу без возможности расшифровать его содержимое.
7. **Расшифровка**: Боб своим закрытым ключом расшифровывает `aes_key`, а затем с помощью `aes_key` и `nonce` расшифровывает текст сообщения.
