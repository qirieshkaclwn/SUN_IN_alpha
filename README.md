# SUN_IN_alpha

Безопасный WebSocket-мессенджер со сквозным (E2E) шифрованием, PKI-аутентификацией (X.509 сертификаты, challenge-response), браузерным веб-клиентом (Web Crypto API) и контейнеризацией в Docker с PostgreSQL.

---

## 🚀 Основные возможности

- **Сквозное (End-to-End) шифрование**: Сообщения шифруются в браузере отправителя и расшифровываются только в браузере получателя (гибридная схема: **RSA-OAEP SHA-256 + AES-256-GCM**). Сервер видит только шифротекст и не может прочитать переписку.
- **Инфраструктура открытых ключей (PKI)**: Встроенный доверенный корневой удостоверяющий центр (Private Root CA), проверяющий и подписывающий запросы на клиентские сертификаты.
- **Правило «1 сертификат на 1 ник»**: В базе данных PostgreSQL никнейм является первичным ключом (`PRIMARY KEY`). Повторный выпуск сертификата на уже зарегистрированный никнейм блокируется сервером.
- **Challenge-Response аутентификация**: Сервер генерирует случайный криптографический `nonce` (32 байта), клиент подписывает его своим закрытым RSA-ключом (`RSASSA-PKCS1-v1_5 SHA-256`), подтверждая владение ключом из сертификата.
- **Хранение в браузере**: Закрытый ключ и выданный сертификат автоматически сохраняются в `localStorage` (`sun_in_key_<ник>` и `sun_in_cert_<ник>`). При повторном подключении новый сертификат не запрашивается.
- **Резервное копирование и перенос (.enc)**: Экспорт и импорт связки закрытого ключа и сертификата в зашифрованный файл `<ник>.enc` (парольная защита по алгоритму AES-256-GCM + SHA-256).
- **Чистый веб-клиент**: Работает прямо в браузере на JavaScript с использованием стандартного Web Crypto API (`window.crypto.subtle`) и компактной автономной библиотеки `@peculiar/x509` (без Python на клиенте и без тяжелых внешних зависимостей).
- **Direct WebSocket Transport**: Сервер работает по протоколу WebSocket (`ws://host:port`) и одновременно отдает статику клиента по HTTP (`http://host:port/`). Промежуточный gateway не требуется.
- **Контейнеризация**: Полная конфигурация `docker-compose.yml` (сервис сервера `sun_in_server` + сервис базы данных `sun_in_db` PostgreSQL 16 с автоматическим применением миграций).

## ⚡ Быстрый запуск

### Способ 1: В Docker (Рекомендуемый)

Требуется установленный **Docker Desktop**.

1. Запустите контейнеры:
   ```bash
   docker compose up --build -d
   ```
2. Откройте в браузере:
   - **Веб-клиент:** [http://localhost:8888/](http://localhost:8888/)
   - **Корневой сертификат CA:** [http://localhost:8888/private_ca.crt](http://localhost:8888/private_ca.crt)
   - **WebSocket-эндпоинт:** `ws://localhost:8888`
3. Управление контейнерами:
   - Просмотр логов: `docker compose logs -f`
   - Остановка: `docker compose down`

### Способ 2: Локальный запуск (Python)

1. Установите зависимости:
   ```bash
   pip install -r server/requirements.txt
   ```
2. Запустите сервер:
   ```bash
   python -m server.main
   ```
   *(При отсутствии запущенного PostgreSQL сервер автоматически переключится в отказоустойчивый fallback-режим с in-memory хранилищем).*
3. Откройте страницу [http://127.0.0.1:8888/](http://127.0.0.1:8888/) в браузере.

## 📡 Протокол передачи данных

Все сообщения передаются по **WebSocket** в виде текстовых фреймов с полезной нагрузкой в формате **JSON (UTF-8)**.

### Формат базового пакета:

```json
{
  "version": 1,
  "type": "packet_type",
  "timestamp": 1773595200,
  "from": "alice",
  "to": "bob",
  "text": "base64_ciphertext...",
  "nickname": "alice",
  "client_cert": "-----BEGIN CERTIFICATE-----\n...",
  "csr": "-----BEGIN CERTIFICATE REQUEST-----\n...",
  "enc_key": "base64_encrypted_aes_key...",
  "nonce": "base64_aes_gcm_nonce...",
  "signature": "base64_signature...",
  "event": "auth_success",
  "error": "error_message"
}
```

### Типы пакетов:

| Тип пакета | Направление | Описание |
|------------|-------------|----------|
| `cert_enroll` | Клиент → Сервер | Запрос на выпуск сертификата по сформированному в браузере CSR |
| `cert_enroll_response` | Сервер → Клиент | Ответ с подписанным сертификатом клиента |
| `auth_init` | Клиент → Сервер | Инициация процедуры входа с указанием никнейма и сертификата |
| `auth_challenge` | Сервер → Клиент | Одноразовый криптографический `nonce` от сервера |
| `auth_proof` | Клиент → Сервер | Цифровая подпись `nonce` закрытым ключом клиента |
| `key_request` | Клиент → Сервер | Запрос сертификата и открытого ключа собеседника по никнейму |
| `key_response` | Сервер → Клиент | Ответ с сертификатом запрашиваемого пользователя |
| `message` | Клиент ↔ Сервер | Сквозное зашифрованное сообщение (`text`, `enc_key`, `nonce`) |
| `event` | Сервер → Клиент | Системные события (`auth_success`, `user_joined`, `user_left`, `users_list`) |
| `error` | Сервер → Клиент | Сообщение об ошибке валидации, авторизации или формата |

## 🔐 Детальный процесс работы и криптография

### 1. Подключение и проверка локального хранилища
При нажатии **Connect** клиент открывает WebSocket-соединение с `ws://host:port`.
Браузер проверяет `localStorage`:
- `sun_in_key_<nickname>` (RSA private key в формате PKCS#8)
- `sun_in_cert_<nickname>` (X.509 certificate в формате PEM)

### 2. Первичный выпуск сертификата (если ключей нет)
1. Браузер средствами Web Crypto API генерирует ключевую пару RSA-2048 (`RSASSA-PKCS1-v1_5 SHA-256`).
2. С помощью библиотеки `x509.js` формируется запрос на сертификат PKCS#10 (CSR) с `CN=<nickname>, O=SUN_IN, C=RU`, подписанный новым закрытым ключом.
3. Клиент отправляет пакет `cert_enroll` с никнеймом и CSR.
4. Сервер:
   - Проверяет, не был ли никнейм зарегистрирован ранее (запрос в таблицу `certificates` PostgreSQL).
   - Если свободен — подписывает CSR ключом `private_ca.key` (срок 365 дней).
   - Сохраняет сертификат в PostgreSQL (`INSERT INTO certificates`).
   - Возвращает пакет `cert_enroll_response`.
5. Браузер сохраняет закрытый ключ и сертификат в `localStorage`.

### 3. Принцип «1 сертификат на 1 ник»
- В базе данных никнейм является `PRIMARY KEY`:
  ```sql
  CREATE TABLE IF NOT EXISTS certificates (
      nickname VARCHAR(255) PRIMARY KEY,
      cert_pem TEXT NOT NULL,
      created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
  );
  ```
- Если злоумышленник попытается запросить сертификат на чужой ник, сервер возвращает ошибку:  
  `Сертификат для никнейма <ник> уже был выдан ранее`.
- При входе (`auth_init`) сервер дополнительно сверяет предъявленный сертификат с оригиналом из базы данных.

### 4. Аутентификация (Challenge-Response)
1. Клиент отправляет `auth_init` с сертификатом.
2. Сервер проверяет подпись корневого CA, срок действия и `CN == nickname`.
3. Сервер отправляет `auth_challenge` со случайным `nonce` (32 байта).
4. Клиент подписывает `nonce` своим закрытым ключом:
   ```javascript
   const signature = await window.crypto.subtle.sign(
     { name: "RSASSA-PKCS1-v1_5" },
     mySignKey,
     nonceBytes
   );
   ```
5. Клиент отправляет подпись в `auth_proof`.
6. Сервер верифицирует подпись открытым ключом из сертификата и возвращает событие `auth_success`.

## 🛡️ Сквозное гибридное шифрование (E2EE)

Для объединения высокой скорости симметричного шифрования и безопасности асимметричной криптографии применяется **гибридная схема**:

```text
┌────────────────────────────────────────────────────────────────────────┐
│ АЛИСА (Отправитель)                                                    │
├────────────────────────────────────────────────────────────────────────┤
│ 1. Исходный текст: "Привет, Боб!"                                      │
│ 2. Сессионный ключ: aes_key = random(256 бит)                          │
│ 3. Вектор инициализации: nonce = random(12 байт)                       │
│ 4. Шифрование текста: ciphertext = AES_256_GCM(plaintext, aes_key)    │
│ 5. Запечатывание ключа: enc_key = RSA_OAEP_SHA256(aes_key, bob_pubkey) │
│ 6. Отправка пакета message: { text, enc_key, nonce }                   │
└────────────────────────────────────────────────────────────────────────┘
                                    ↓
                         СЕРВЕР (МАРШРУТИЗАТОР)
          (видит только шифротекст, расшифровать не может)
                                    ↓
┌────────────────────────────────────────────────────────────────────────┐
│ БОБ (Получатель)                                                       │
├────────────────────────────────────────────────────────────────────────┤
│ 1. Получен пакет: { text, enc_key, nonce }                             │
│ 2. Расшифровка ключа: aes_key = RSA_OAEP_decrypt(enc_key, bob_privkey) │
│ 3. Расшифровка текста: plaintext = AES_256_GCM_decrypt(text, aes_key)  │
│ 4. Отображение сообщения в чате: "Привет, Боб!"                        │
└────────────────────────────────────────────────────────────────────────┘
```

## 💾 Резервное копирование и перенос (.enc)

Для переноса identity на другое устройство предусмотрена система зашифрованных бэкапов:
- **Экспорт (Export .enc)**: Закрытый ключ и сертификат упаковываются в бинарный блок и шифруются алгоритмом **AES-256-GCM**. Ключ шифрования формируется из введенного пользователем пароля через хэш **SHA-256**. Файл скачивается с расширением `<nickname>.enc`.
- **Импорт (Import .enc)**: Пользователь вводит пароль, выбирает файл бэкапа — данные расшифровываются прямо в браузере и помещаются в `localStorage`.
